## Objective and Release Boundary

Release WCRT 1.0.0 after the required C99 hosted-library profile is specified,
implemented, reviewed, verified on x86, x64, and ARM64, and supported by a
completed release-readiness record. C89 behavior and the already baselined
Microsoft-compatibility interfaces remain regression obligations.

The remaining Microsoft CRT compatibility roadmap, C11 and later standards,
and optional `wWinMain` startup are not prerequisites for 1.0.0. `wWinMain`
may enter 1.0.0 only after the wide-character prerequisites pass and without
delaying C99 closure; otherwise it moves to 1.1.0.

## Planning Basis and Uncertainty

Repository history shows that the first controlled C99 tranche, REQ-0021
through REQ-0026, was baselined and implemented during 2026-07-26 through
2026-07-27. That tranche is useful structural evidence but is not a reliable
effort baseline because phase time and defects were not recorded. The estimates
below are therefore bottom-up ranges, not commitments.

Size is expressed as controlled conformance units (requirements with matching
test specifications), plus an indicative implementation-size range. Effort is
focused engineering time and excludes interruptions. Forecast dates shall be
set after two tranches have actual velocity; until then, the schedule is
expressed as sequential effort.

## Required Work-Item Record

Before each tranche begins, create `docs/work/c99-tN-<name>.md` containing:

| Field | Required content |
| --- | --- |
| Scope and size | Requirement IDs, expected changed files or LOC range, exclusions |
| Estimate | Hours by plan/specify/design/implement/review/verify/postmortem and forecast range |
| Quality plan | Reviews, analyses, test levels, targets, and evidence |
| Time log | Date, phase, focused minutes, excluded interruption, note |
| Defect log | ID, type, injected phase, removed phase, fix minutes, related artifact |
| Checklist | Requirement, design, code, test, documentation, compatibility findings |
| Postmortem | Planned versus actual size/effort/schedule/defects and process changes |

Defect types are `requirements`, `design`, `interface/ABI`, `algorithm`,
`numeric`, `resource/lifetime`, `build/tooling`, `test`, and `documentation`.

## Completion Criteria for Every Tranche

- Planned requirements are reviewed and baselined before their implementation
  is represented as conforming.
- Each requirement maps to a controlled specification, runner, manifest entry,
  implementation, and retained result.
- Personal design/code/test review is complete and findings are dispositioned.
- Header self-containment, C89 isolation, supported-target ABI, and applicable
  Windows 2000 x86 imports are verified.
- C89, earlier C99, startup, source-quality, traceability, evidence, build, and
  consumer tests remain green.
- Implementation-defined behavior, deviations, risks, and compiler-blocked
  facilities are documented rather than silently omitted.
- Planned and actual measures and the postmortem are recorded.

## 1.0.0 Release Gates

1. REQ-0027 through REQ-0042 are either baselined and Pass, or explicitly
   classified by the C99 profile as optional, compiler-blocked, or an approved
   deviation consistent with the release claim.
2. No required C99, C89, compatibility, traceability, source-quality, build,
   package, or consumer result is Fail or unknown on a supported target.
3. The supported TinyCC versions, Windows data models, ABI, implementation-
   defined behavior, deviations, and platform validation tiers are published.
4. Phase 0 and C89 documentation gates relevant to the C99 release are closed.
5. Public API and ABI compatibility policy for the 1.x line is approved.
6. Release documentation, dependency provenance, exact artifact digests,
   signing/timestamp evidence, Defender results, rollback instructions, and
   support policy are complete.
7. A release-readiness record identifies the source revision and approves the
   exact 1.0.0 artifact set.
8. The release postmortem records estimate accuracy, defects, escaped issues,
   and selected process improvements.

## Principal Risks and Responses

| Risk | Response and decision point |
| --- | --- |
| TinyCC lacks consistent complex or type-generic behavior | T0 confirms `_Generic` selection but TinyCC 0.9.28rc rejects `_Complex` on all targets; block T5 design until a compiler change, conforming alternative, or approved compiler-blocked/deviation decision is baselined |
| Windows `long double` differs from abstract C99 expectations | Record each ABI and make tests follow the documented implementation model |
| Wide streams and UTF-16 expand scope | Baseline REQ-0033 design before T3 implementation; defer optional `wWinMain` first |
| Math accuracy work exceeds estimate | Define accuracy method and reference data in each test specification before implementation |
| Legacy Windows imports regress | Automate import inspection in T0 and gate every later tranche |
| Roadmap status drifts from evidence | Update roadmap checkboxes only in the same change that adds passing controlled evidence |
| Release controls remain deferred | Treat their closure as R1 deliverables, not post-release cleanup |

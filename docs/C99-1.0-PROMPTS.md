# C99 to 1.0.0 Execution Prompts

**Content type:** Execution prompt catalog

**Status:** Proposed

**Model guidance checked:** 2026-08-04

## How to Use This Catalog

Use one fresh Codex task per tranche so its context remains focused. Run the
kickoff prompt first, use the implementation prompt for the named tranche, and
finish with the review and postmortem prompts. Replace bracketed values before
submitting. Do not combine tranches merely to reduce the number of tasks.

Model names below follow the current GPT-5.6 family:

- **GPT-5.6 Sol** is the flagship choice for difficult design, implementation,
  debugging, and conformance judgment.
- **GPT-5.6 Terra** is the balanced choice for bounded planning,
  documentation, test integration, and routine corrective work.
- Start at the listed reasoning effort. Increase it only after a concrete
  failure or when the prompt explicitly calls for a final quality-first audit.

These prompts authorize in-scope local edits and non-destructive validation.
They do not authorize publishing releases, pushing changes, external writes,
destructive actions, or scope expansion.

## 0 — Start or Resume Any Tranche

**Model:** GPT-5.6 Terra, medium reasoning

```text
We are starting [TRANCHE] from docs/C99-1.0-WORK-PLAN.md. Follow
docs/PROJECT-PROCESS.md and update [WORK-LOG] as the WSP personal-process
record. Inspect the repository before planning. Reconcile the work-plan
assumptions with current evidence, refine the size and phase-effort estimates,
and record risks, dependencies, completion criteria, and the quality plan.

Do not implement yet. Return the proposed tranche baseline, discrepancies you
found, and the exact implementation order. Treat requirements, tests, C89
isolation, x86/x64/ARM64 behavior, and retained evidence as completion work.
```

## Postmortem After Every Tranche

**Model:** GPT-5.6 Terra, medium reasoning

```text
Complete the postmortem for [TRANCHE] in [WORK-LOG]. Inspect the recorded plan,
diff, review findings, test evidence, time entries, and defect entries. Compare
planned and actual size, phase effort, schedule, defects, and quality activity.
Do not invent missing measures; label them unavailable and recommend how to
capture them next time.

Identify estimation errors, recurring defect patterns, escaped or late-removed
defects, and no more than three concrete process/checklist improvements. Update
the next tranche estimate only when the evidence supports a change. Make only
documentation changes to the work log and controlled process artifacts; do not
alter product behavior.
```

## When a Tranche Fails Verification

**Model:** GPT-5.6 Sol, high reasoning

```text
Diagnose the failing [TEST/BUILD] for [TRANCHE]. Inspect the controlled
requirement, test specification, implementation, logs, and most recent relevant
change. Determine whether the defect is in requirements, design, interface/ABI,
algorithm, numeric behavior, resource/lifetime handling, build/tooling, test,
or documentation. Record the defect in [WORK-LOG], including injection/removal
phase and fix effort when known.

Implement the smallest in-scope correction that satisfies the controlled
requirement, add or strengthen a regression test when needed, and re-run the
affected test plus required earlier regressions. Do not weaken expected results
to make the test pass. Report root cause, correction, and evidence.
```
